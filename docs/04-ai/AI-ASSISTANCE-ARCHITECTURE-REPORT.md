# AI Assistance & Agentic Architecture — Code-Based Review

**Scope:** Current repository implementation, traced from frontend entry points through Flask routes, provider routing, tool execution, persistence, retrieval, and governance. This is a code review, not a claim that every route was exercised against a live database/provider.

## Executive summary

NexLab has two overlapping AI surfaces:

1. A shared, role-aware **AI Harness** in the five main product shells. It sends chat/agent requests to `/ai/harness/message`, where a role-specific tool map, an LLM planner, optional document/web retrieval, and direct tool execution produce a response. Staff tools can make real database changes during the chat turn.
2. Separate, more focused AI endpoints for lab hints, code assistance, topic explanations, viva question generation/evaluation, and a legacy institution-admin agent API.

The main harness persists threads and messages, builds prompts from role/page/history/memory/document context, and can chain up to six tool calls. The provider client tries DeepSeek first, then a rotating Groq model pool, then OpenRouter and Gemini. If all configured providers fail, it now returns no answer rather than manufacturing canned Stack/quiz content.

The code review found important governance and data-scope weaknesses: the AI gate is bypassed by several instructor-generation routes; RAG document scope is not consistently enforced (including a `doc_id` path that skips tenant scoping); staff tools can mutate data in ordinary “chat” mode; and the confirmation endpoint does not prove that a submitted action came from a pending action owned by the caller. Treat the UI confirmation card as a usability affordance, not a security boundary.

## Frontend entry points

- `frontend/components/layout/AgentChatPanel.tsx` is the shared Harness UI. It is mounted from `StudentShell`, `InstructorShell`, `InstitutionShell`, `IndividualShell`, and `AdminShell`.
- Role configuration changes its label, suggested prompts, and whether the UI offers an agent-mode toggle. Students and independent learners (`platform_user`) are configured as Socratic-only; instructors, institution admins, and platform admins can select chat/agent mode.
- The panel sends the request through `frontend/services/ai.service.ts` to `/api/ai/harness/message` (same-origin), which is served by a dedicated Next.js route handler (`frontend/app/api/ai/harness/message/route.ts`) that proxies to Flask with a 190-second upstream wait. The browser client timeout is 200 seconds. This replaced the generic rewrite proxy, whose 30-second timeout killed long agent turns mid-flight. If a long agent task still outlives the HTTP wait, the panel polls the caller-owned session (or, for brand-new conversations, the session list) and renders the persisted assistant message instead of leaving the thread empty. It renders returned tool calls, citations, generated documents, and pending-action cards.
- Separate UI entry points call `/ai/code-assist` from the compiler/playground and `/ai/hint` from the live lab. These are not the same request path as the shared panel.
- The backend emits Socket.IO events for tool starts/results and response tokens, but the inspected frontend has no listeners for those `ai:*` events. The shared panel therefore waits for the completed HTTP response rather than visibly streaming those events.

## Main request and execution flow

1. `@require_auth` establishes the authenticated user and role in Flask request context. `/ai/harness/message` accepts a prompt (up to 4,000 characters), mode, optional `doc_id`, web-search flag, session ID, and page context. Students/platform learners are forcibly kept in `chat` mode.
2. The route creates or loads the caller-owned `AdminChatSession`, stores the user message, and supplies recent history, saved page context, and compact memory to `run_harness_turn`.
3. The harness selects `get_tools_for_role(role)`, recognizes supported slash commands, and ranks a short tool catalog from prompt and page-route tokens. The planner prompt requests a strict JSON `{tool,args}` response. It then calls the chosen role tool directly and feeds the result back for up to six planning/tool turns (with a nominal 32,000-token turn budget).
4. If a provider answers but emits no tool call, a deterministic keyword-based fallback may invoke a role tool. The review changed this so provider unavailability is tracked separately and skips that fallback: with no planner response, no tool/database action is run.
5. A second model call synthesizes the answer from tool results. If the model is unavailable, the harness creates a deterministic summary from actual tool results. Student/platform-user answers then pass through a code-level Socratic filter that attempts to remove long code blocks.
6. The route stores the assistant message, tool calls, sources, pending action, generated-document metadata, token total, and a per-institution `AIAgentRun` where applicable. Session history and messages live in the database; users can rename, pin, load, or delete their own threads. Older messages may be summarized into rolling compact memory.

### Tool permissions and confirmation

- The registry in `backend/app/ai/role_tools.py` returns different tool sets for students, platform learners, instructors, institution admins, and platform admins. The normal harness can only resolve tool names present in the role’s map.
- Learner routes are also explicitly blocked from the administrative action-execution endpoint. Confirmed actions go through `execute_role_action`, which has action-specific server-side role checks and an allow-listed set of action implementations.
- **Mode is not an authorization boundary.** The harness routes and executes role tools in both chat and agent modes; mode mostly changes UI/prompt framing. Non-destructive staff operations—including authoring, publishing, scheduling, enrollment, grading, and workspace/report creation—can run immediately in either mode.
- Only tools in `CONFIRM_ACTION_NAMES` or tools returning `requires_confirmation` produce pending-action cards. Most ordinary creation/setup operations are not paused for confirmation.
- The action-execution endpoint accepts an action payload from the authenticated caller; it does not verify that the payload exactly matches a pending action on a message owned by that caller. The role checks still matter, but the UI card itself is not proof of consent. The optional `message_id` is looked up without an ownership filter when clearing the pending action.

## Other AI surfaces

`backend/app/ai/routes.py` also defines focused routes for progressive lab hints, multi-turn help chat, viva generation/evaluation, code assistance, and topic explanation. The main focused hint/chat/code-assist routes use `guarded_ai_call`; hints additionally have a legacy request-count meter and level-based grading deductions. Code-assist modes are prompt-based (hint, explain error, review, ask); the route sends code, diagnostics, output, and question text to the model—it does not execute that code.

There is also an older `/ai/agent/query` + `/ai/agent/runs/.../apply` path for institution admins, implemented through `backend/app/ai/agent.py`. The frontend service still exposes it, but a repository search found no current UI call site; the shared panel uses the Harness endpoints instead. Legacy `/ai/chat/*` paths remain aliases of the Harness session/message/action routes.

## Provider and model routing

The current source order in `backend/app/ai/groq_client.py` is:

1. **DeepSeek** (`DEEPSEEK_MODEL_QUALITY` or `DEEPSEEK_MODEL_FAST`, defaults named DeepSeek V4 Pro/Flash), attempted first. Its key is now read only from `DEEPSEEK_API_KEY`; if absent, this provider is skipped. The read timeout now scales with request size — `DEEPSEEK_TIMEOUT_SECONDS` (default 15s) for small calls, raised to 45s for large generations (planner/content authoring), which need a longer window on a slow-but-healthy endpoint while still failing over when the endpoint is truly stalled. This replaced the old flat 90s. The default base URL in source is a non-DeepSeek-domain proxy hostname, configurable with `DEEPSEEK_BASE_URL`; verify its ownership, data handling, and contractual status before sending student or institutional content there. In the regression environment this endpoint was unreachable (read timeouts) on every call, so all serving fell to the OpenRouter free fallback.
2. **Groq model rotation**, using the `fast` or `quality` pool, overridable with `GROQ_POOL_FAST` / `GROQ_POOL_QUALITY`. The checked-in defaults currently name Qwen 3.8 27B and OpenAI GPT-OSS 120B/20B. Rate-limit failures cool a model for 60 seconds; retired/bad-model responses for an hour; server/network errors for five minutes.
3. **OpenRouter** free-model rotation when Groq is unavailable/exhausted and an OpenRouter key exists. For large generations (max_tokens ≥ 2000) the non-reasoning models are tried first and the request sets `reasoning: {effort: "low"}`, which cuts free-model generation roughly in half without hurting document quality. Connect/read timeouts are `(10s, 120s)` for large calls and `(10s, 45s)` otherwise. `response_format: json_object` is available via `json_mode`, but the regression round found it breaks reasoning separation on the free fallback model (chain-of-thought leaks into the content and consumes the token budget), so content generation does not use it and relies on the lenient balanced-JSON extractor instead.
4. **Gemini** fallback models when configured.
5. **No answer** when every configured provider fails. The former built-in “Studio AI Engine” response generator has been removed; it could return Stack-specific examples/quiz/assignment content unrelated to the user’s actual request and could have been persisted by content-generation callers.

DeepSeek is attempted before Groq regardless of the pool name. OpenRouter/Gemini usage is approximated from character counts where provider usage is not returned. The central gate currently labels every non-Gemini provider as `groq` in `AIUsageLog`, so DeepSeek/OpenRouter/provider attribution is inaccurate (and cost reporting may be unreliable).

## Persistence, context, and retrieval

- **Conversation persistence:** `AdminChatSession` and `AdminChatMessage` store threads, roles, modes, page context, messages, tool observations, sources, pending actions, generated-document metadata, token counts, and whether the Socratic filter ran. Sessions are user-owned; there is no expiry in the session model.
- **Prompt context:** live role/user/institution details, page context, recent chat history, compact memory, selected tool descriptions, and—when retrieved—document excerpts are incorporated into the planner/synthesis prompts. The recent history passed to the planner is short (up to five previous messages); older turns can be summarized into compact memory.
- **Role memory:** `learner_context.py` builds student/platform-learner snapshots and durable goals/notes, instructor context, and platform-admin context. The call-site bug that referenced an undefined `current_user` has been fixed to pass the authenticated user object. However, `build_role_context` has no `institution_admin` branch, so institution admins still receive no role snapshot from that function.
- **RAG uploads:** PDF, DOCX, XLSX, CSV, Markdown, and TXT are text-extracted into overlapping chunks. Embeddings use Google’s embedding SDK/key when available; otherwise the helper can make deterministic local hash embeddings. Search prefers pgvector semantic similarity where available, then uses TF-IDF fallback. At most four chunks are included in the Harness context. Retrieval runs when a document is attached or the prompt contains selected document-related keywords; web search is separately opt-in.
- **Generated documents:** tool functions can save Markdown/CSV/XLSX files and an `AIGeneratedDocument` database record for download. The model metadata includes a seven-day expiry timestamp; this review did not verify a cleanup job that removes expired files/rows.

## Findings and risks (remaining unless marked fixed)

### High priority — tenant/document scope and external data

1. **RAG scopes are not enforced as their schema suggests.** `search_scoped_documents` filters by `doc_id` alone when one is supplied, without checking institution/uploader ownership. Without `doc_id`, institution users are effectively searched against every document bearing that institution ID; `scope_type`/`scope_id` are not included in the retrieval predicate. Document listing also returns institution-wide records. Consequences: personal/section/course scope labels do not provide isolation, and a known document ID can bypass tenant scoping. Review and fix authorization at list, retrieval, upload-scope assignment, and deletion boundaries.
2. **Generated-document download lacks tenant validation for institution admins.** A caller with the `institution_admin` role may download another user's generated document by ID without verifying that document’s `institution_id` matches the caller’s tenant. Add a tenant check.
3. **Prompts leave the application.** User prompts, code, error/output context, page data, and retrieved document excerpts may be sent to DeepSeek’s configured endpoint, Groq, OpenRouter, or Gemini. The DeepSeek default endpoint is a third-party proxy hostname. Confirm provider contracts, retention/training settings, region, and institutional consent; minimize sensitive prompt data.
4. **Retrieved text is untrusted input.** Document/web excerpts are inserted into the prompt context; the code does not add a strong separate trust boundary against prompt-injection instructions embedded in those sources.

### High priority — governance, side effects, and audit

5. **The AI gate is not universal.** Some instructor AI routes call `groq_chat`/`groq_single` directly, notably experiment content/viva generation in `backend/app/instructor/content.py`, test-case generation in `backend/app/instructor/routes.py`, and checkpoint suggestions in `backend/app/instructor/features.py`. These paths do not consistently pass through the central feature-policy/quota/usage-log gate. The student viva evaluation fallback that directly retried a provider after any gate error has been removed; it now returns 403/429 for policy/quota denials and 503 for evaluation failure rather than bypassing the gate or assigning a synthetic neutral score.
6. **Governance checks fail open in some database-error cases.** `guarded_ai_call` fails open when platform/institution policy reads or usage-log/quota reads fail. That improves availability but means governance/quota enforcement is not fail-closed during certain database faults.
7. **Confirmation is mostly UI-level.** The staff harness intentionally auto-runs most non-destructive writes, and the action endpoint accepts client-provided payloads without binding them to a caller-owned pending-action record. Reassess which writes need explicit confirmation and validate confirmation server-side.
8. **Provider usage attribution is wrong for non-Gemini providers.** The gate’s provider mapping defaults to `groq`; correct provider/model tagging before relying on provider-level usage or cost comparisons.

### Medium priority — reliability and behavior

9. **Planner ambiguity can still trigger writes.** When a provider returns text but no tool call, the deterministic keyword fallback can invoke a role tool. Provider-unavailable turns now skip that fallback, but ambiguous successful model replies can still reach it. The regression round added a guard so an explicit “create a NEW experiment/lab” request is never routed to a tool that edits an existing experiment (it is forced into the dedicated builder with deterministically extracted arguments); the keyword fallback itself is now conservative and requires a clearer create-intent. Still, ambiguous replies for other write verbs can reach the fallback, so keep tightening it.
10. **The student guardrail is not a hard safety boundary.** It is a code-level text filter after generation; it does not constrain every separate endpoint, prove answer correctness, or guarantee that all solutions are removed.
11. **The main panel does not consume emitted Socket.IO events.** The UI waits on the HTTP response, so the server’s token/tool event emission does not currently deliver visible streaming in that component.
12. **Configuration has development defaults.** `backend/app/config.py` includes placeholder defaults for Flask/JWT signing secrets and a local database URL. Production must override them with strong managed secrets and production database configuration; do not rely on source defaults.

## Frontend regression round — real-world task verification

This round exercised the live system from a real browser (Playwright/Chromium) against the running Flask + Next.js + Postgres stack, using an isolated temporary tenant (“AI Regression Temporary …”) with real student/instructor/institution-admin/platform-admin accounts and a real saved student submission containing a deliberate off-by-one bug. The primary DeepSeek endpoint was unreachable in this environment, so all model serving came from the OpenRouter free fallback, which is slower and nondeterministic than a healthy primary would be.

**Scenarios exercised and outcomes:**

- **Student Socratic code review (from the dashboard panel).** 201, session created, tool ran, and the returned Level-1 hint correctly targeted the low/high index invariant without revealing the fix. Confirmed the learner path reads the real saved `CodeVersion`/`CodeAttempt` data.
- **Instructor agent builds a complete experiment (real task).** The harness planned and executed `build_complete_experiment_suite`, which persisted and published a real experiment: 3 pages, 5 test cases (visible + hidden), a readiness quiz, viva Q&As, SPARK checkpoints, a runnable solution, a starter scaffold, and a standalone interactive HTML visualizer. The content was genuinely topic-specific (verified by reading the stored rows and the written simulation file).
- **The new experiment is visible to the student.** After the instructor’s AI build, the enrolled student’s subject listing shows the newly published experiment — closing the real instructor→student loop.
- **Resilience defects found and fixed in this round** (see changes below): a boolean argument crashing the builder, a 30s proxy timeout killing long turns, the planner misrouting a “new experiment” request to an existing-experiment edit tool, JSON parsing failing on reasoning-model preambles, free-model generations stalling for minutes, and placeholder/echo content being silently persisted.

**Residual environmental caveats (not code defects):** with the primary provider unreachable and only the free fallback available, large agent builds can take minutes and the free model is sometimes truncated (the builder now retries once and, if both attempts are incomplete, creates nothing and says so rather than persisting filler). Rate-limit bursts on the free key can make a turn report “provider unavailable,” which the harness now communicates honestly with no database side effects. A healthy primary provider is expected to make these paths fast and reliable.

## Student & platform-admin live round (second regression)

A second browser-driven round verified the two remaining roles against the rebuilt SKIT baseline (walkthrough + make_activity data), with DeepSeek intermittently stalling and Groq (`qwen/qwen3.8-27b`, `openai/gpt-oss-*`) serving as the working leg.

**Scenarios exercised and outcomes:**

- **Student Socratic review of a real saved attempt.** Rahul (student) had a saved `CodeVersion`/`CodeAttempt` on “Implement Binary Search on a Sorted Array” (buggy `high = len(arr)` initialization, runtime `IndexError`). From the dashboard’s “Ask Socratic Tutor” panel the tutor called `analyze_my_code` + `get_socratic_hint`, named the experiment, quoted the exact crashing line, and gave a Level-1 conceptual hint about the initial `high` bound; a follow-up escalated to Level-2 structural checkpoints (mid calculation / loop condition / bound updates) with a trace exercise — still zero solution spoiler and no corrected code block. No 5xx, no uncaught browser errors.
- **Platform-admin copilot (super-admin, Agent & Action mode).** Three turns: (1) global overview + institution list — the AI’s numbers matched the database exactly (1 institution SKIT, 1/1/1/1 users by role, per-institution token totals, platform config flags); (2) User-360 stats for the SKIT student (accurate zero-engagement profile); (3) **real governance action** — `autonomous_onboard_institution` provisioned a temporary tenant end-to-end (Institution + institution_admin user + AcademicYear + AIPolicy 500k quota), verified row-by-row in Postgres, then removed in an FK-ordered cleanup.

**Defects found and fixed in this round:**

1. **Every platform-admin AI turn 500’d (FK violation on `admin_chat_messages`).** Chain: `platform_metrics_daily` was never created (raw-SQL table from `migrate_admin_p3.py`, not built by `db.create_all`) → `_admin_snapshot`’s raw `SELECT` aborted the Postgres transaction → `build_role_context` swallowed the exception **without a rollback** → the next `commit()` in `_log_usage` silently turned into a rollback (Postgres converts COMMIT-after-error into ROLLBACK; SQLAlchemy believes the flushed work committed) → the uncommitted chat-session row was lost → the final assistant-message INSERT violated the FK. Fixes: `migrate_admin_p3.py` now runs in `setup.sh` (table created); `_admin_snapshot` fails soft on the raw query; `build_role_context` always rolls back on exception so a context-engine failure can never poison the request transaction.
2. **Platform-admin AI tools referenced non-existent `Institution` columns** (`subdomain`, `status`, `max_students`, `max_instructors`, plus ordering by a missing `created_at`) — `list_platform_institutions`, `autonomous_onboard_institution`, `autonomous_update_tenant_or_platform_config`, and the Phase-4 confirmed actions all crashed on first use. Fixed to the real schema: `code` (unique tenant identifier, derived with a uniqueness loop for onboarding), `is_active`/`onboarding_status` for status, actual seat counts (seat caps are not tracked per institution — the tool now says so), `onboarded_at` for ordering. Verified by direct unit calls and by the live browser onboarding.
3. **Groq model `qwen/qwen3.8-27b` rejected `reasoning_effort`** (400 “unexpected keyword argument … did you mean reasoning_format?”), which rotated the model out for 300s on every turn. The Groq leg now sends only `reasoning_format='hidden'` to that model (`REASONING_EFFORT_MODELS` is a separate opt-in set), and any model that 400s on a reasoning parameter is retried once without it instead of being rotated out.
4. **Uncaught `RangeError: Incorrect locale information provided` in dev.** `@tanstack/react-query-devtools` calls `new Intl.Locale(navigator.language)` at chunk load; headless/POSIX-locale environments report non-BCP-47 tags like `en-US@posix`. `providers.tsx` now sanitizes `navigator.language` before the devtools chunk evaluates (dev-only, no-op for valid tags).

All temporary scenario data (student attempt rows, both test chat sessions, usage/agent-run/learner-memory rows, and the temporary institution) was removed in committed FK-ordered transactions; the database was verified back to the clean SKIT baseline (1 institution / 4 users / 3 experiments / 3 sessions / 3 grades, 0 test artifacts).

## Normal platform-user (self-learner) live round

A third browser-driven round verified the `platform_user` role — the normal account a visitor creates via self-registration ("Ask AI Coach" / NexLab Coding Coach, chat-only, Socratic-protected). One environmental limitation: the Brevo account has an IP allow-list that rejects this sandbox's egress IP (401 "unrecognised IP"), so the physical OTP email cannot be delivered here; only that one step was simulated (the sent OTP row was marked verified, then the real `/otp/verify` and `/api/auth/register` endpoints ran normally and created a `platform_user` with no institution).

**Scenario and outcome (11/11 automated checks passed):** a freshly registered learner with zero practice history chatted with the coach through the real frontend:

- **Practice stats + weakest areas.** `get_my_practice_stats` returned an honest empty state (all-zero table, "no topics recorded yet") — no invented metrics — and offered next steps.
- **Socratic review of pasted practice code.** The learner pasted a remove-duplicates implementation that returned 2 for `[1,1,2,3,3]`. `analyze_practice_code` traced the write pointer iteration-by-iteration on the real input, asked the exact guiding question ("last unique element is at index 2 — what is the count?"), and hinted "i + 1" **without** writing the fix.

- **Downloadable study plan.** `enroll_and_build_study_plan` produced a real `.md` deliverable card (verified in `ai_generated_documents`) plus a roadmap playlist collection.

The temporary learner account and every row it created (chat session + messages, playground session, collections, generated documents, learner memory, usage logs, OTP row) were removed in a committed FK-ordered transaction; the database was verified back to the exact SKIT baseline.

## Institution-admin ("NexLab AI Copilot") live round

A fourth browser-driven round verified the `institution_admin` role — the tenant operator's "Ask AI Copilot" in Agent & Action Mode (30 tools: analytics/catalog reads, department/section/subject creation, user & governance management, session scheduling, announcements, executive reports, autonomous campus setup, and experiment-suite building). The scenario ran four real-world turns against the SKIT tenant in a real Chromium session:

1. "Give me my institution's academic structure … plus the grades analytics summary for the last 30 days."
2. "How is my student overall? … lab session attendance — any at-risk signal?"
3. "Schedule a 60-minute lab session titled 'DSA Revision Lab' … Section A on 2026-10-28 at 10:00."
4. "Create a new subject called 'Operating Systems Lab' with code OS-LAB-26 under the CSE department."

**First run scored 9/11 and exposed five real code defects (plus one model-behavior gap). All were fixed and the round was re-run to 12/12 with zero tool errors.**

Defects found and fixed:

- **Catalog tool crashed on every call.** `admin_query_academic_catalog_deep` serialized `Subject.semester`, but the `Subject` model has no such column (it has `subject_type`) → `'Subject' object has no attribute 'semester'`. The AI disclosed the error honestly, but the admin got no department/batch/section hierarchy at all. Now serializes the real fields.
- **"Create a subject called '… Lab'" was hijacked into building an experiment.** The forced experiment-intent guard (harness.py) matched `\b(create|…)\b.{0,70}\b(experiment|lab)\b`, so the quoted *subject name* "Operating Systems Lab" triggered `build_complete_experiment_suite`: a junk experiment was created under DSA, the subject was never created, and the turn ended with leaked raw model reasoning. Replaced with `_has_experiment_create_intent`: quoted spans are stripped first (a quoted "lab" is usually an entity *name*, not the object being created), prompts creating another academic entity (subject, department, section, batch, year, course, quiz, exam, session) never trigger the experiment guard, and the match window tightened from 70 to 40 chars. Unit-verified against 12 intent cases (all pass), including both hijack and genuine "create a complete experiment" phrasings.
- **Every subject creation crashed — and the AI claimed success anyway.** `autonomous_create_academic_entity` (plus the campus-setup and legacy `admin_create_subject` paths) constructed `Subject(..., semester=…)` — and one site also `credits=…` — columns that do not exist. Subject creation failed six consecutive times while the model told the admin "Subject created ✅" with a fabricated ID. A serious false-success hallucination. The phantom kwargs are removed; the re-run created the subject for real and the test now verifies the record through the `/api/institution/subjects` endpoint, not just the reply text.
- **`query_analytics_domain(domain='spark')` pointed at a nonexistent function.** `route_map` referenced `app.institution.extended.analytics_spark`, which did not exist → tool error on every SPARK-score query. Implemented the view: institution-wide SPARK 5D aggregation from `student_rankings` (per-student mastery/engagement/effort/efficiency/consistency, weighted overall, rank position, real student names). It returns an honest empty aggregate when no rankings exist yet.
- **`student_get_my_spark_and_skills` used five phantom fields** on `StudentRanking` (`overall_score`, `code_quality_score`, `rank_in_section`, `total_in_section`, `percentile` — none exist). Mapped to the real columns (`rank_score`, `mastery_score`, `engagement_score`, `effort_score`, `efficiency_score`, `consistency_score`, `rank_position`).
- **Student identity was truncated out of tool observations → invented name.** The analytics payloads cap at 4000 observation chars, and `rows_sample` — the only place carrying real student names — sat at the *end* of the student-360 JSON, so it was always cut. With the name invisible, the model answered "your student, Dr. Ramesh Kumar" (the real student is Rahul Sharma). `rows_sample` is now placed first in the payload; the re-run correctly answered "Rahul Sharma (Roll SKIT2026001)" with his three real finals.
- **Harness prompt hardened for false success.** Two rules added to the agent system prompt: (1) planner — if the same tool returns the same error twice, stop retrying and report the failure (previously it burned the whole 6-call budget); (2) final answer — never state a record was created/updated/deleted unless a tool observation shows it succeeded, and never invent names/IDs not present in the observations (say "unavailable" instead).

**Final run: 12/12 automated checks passed, zero tool errors, zero 5xx responses, zero uncaught browser errors.** The catalog turn returned the real CSE department, Sections A & B and CS301/DSA with correct grades (3 graded, avg 82.1%, GPA 3.28, 100% pass); the student turn matched the database exactly (finals 89.7 / 70.7 / 85.9, attendance 1 present / 1 late / 1 absent) and correctly flagged the attendance risk band; the scheduling turn created a real `lab_sessions` row (verified by ID in the confirmation); the subject turn created a real subject verified via API. Provider note: the configured DeepSeek primary was unreachable from this sandbox (read timeouts), so all LLM calls served by the Groq/OpenRouter fallback chain — environmental, with automatic fail-through.

All test artifacts were removed in committed FK-ordered transactions (test lab session, test subject, junk experiment + its content modules/pages/checkpoints/quiz questions/test cases, chat sessions and messages, today's usage/agent-run rows, and test audit rows), and the database was verified back to the exact SKIT baseline (4 users / 1 institution / 3 experiments / 3 lab sessions / 1 subject / 3 grades / 19 baseline audit rows).

## Changes made during this review

- Removed the hardcoded DeepSeek credential fallback. Missing `DEEPSEEK_API_KEY` now skips DeepSeek instead of using a source-embedded credential.
- Removed synthetic Studio fallback content. When all configured providers fail, the provider layer returns no answer; the Harness now also skips its keyword-based write fallback and tells the user that no action ran.
- Fixed the Harness role-context call to pass the fetched authenticated user object; previously an undefined name was swallowed by a broad exception and context was silently omitted.
- Fixed `create_chat_session` to read and validate the submitted `page_context`; previously that handler referenced an undefined variable.
- Removed a student viva evaluation retry that bypassed the AI gate after any exception. Policy/quota denials now remain denials; provider/parse failure does not silently award an automatic neutral score.
- **Frontend timeout for long AI turns.** Added `frontend/app/api/ai/harness/message/route.ts` (Next.js route handler) that proxies the harness message to Flask with a 190s upstream wait and 200s client timeout, replacing the 30s rewrite-proxy cutoff. The rewrite was re-ordered (beforeFiles/fallback) so Socket.IO keeps working and only the harness path uses the long handler.
- **Background-completion polling.** `AgentChatPanel` now detects an HTTP timeout on a long agent task and polls the caller-owned session (or the session list for brand-new conversations) to render the persisted assistant message, so a slow-but-successful build still appears in the thread.
- **Removed placeholder experiment content.** `build_complete_experiment_suite` no longer persists the generic sum/echo template, canned quiz, or default HTML when a topic is requested. It now generates topic-specific material (aim, problem statement, theory, runnable code, an incomplete starter scaffold, test cases, quiz, viva) and a standalone interactive HTML visualizer, validates each field is real and present, and creates nothing (with a clear error) if any required piece is missing or malformed.
- **No invented subjects.** The builder no longer auto-creates a default placeholder subject; it fails cleanly if no subject is available.
- **New-experiment routing guard.** A request to create a NEW experiment/lab is never executed by a tool that edits an existing experiment; it is forced into `build_complete_experiment_suite` with deterministically extracted title/subject/language/requirements. The deterministic keyword fallback now extracts quoted titles/subjects/languages and only fires on clear create-intent.
- **Robust JSON extraction.** `_extract_json` now finds balanced top-level object spans (string/escape aware) and parses leniently, tolerating reasoning-model preambles, placeholder-schema objects, and raw control characters in strings. This fixes planner and content parsing that previously grabbed the wrong object.
- **Fast, reliable free-model generation.** Large OpenRouter generations try non-reasoning models first and send `reasoning: {effort: "low"}`, roughly halving generation time; connect/read timeouts were raised to `(10s,120s)` for large calls. `json_mode` (`response_format: json_object`) was added as an option but is not used for content generation because it broke reasoning separation on the free model.
- **Coercion of model-supplied tool arguments.** `build_complete_experiment_suite` and `build_complete_exam` now coerce planner-supplied strings/booleans/numbers/lists to the expected types (e.g. `language=true` no longer crashes on `.lower()`), and normalize minor format drift in quiz/viva/test-case objects before strict validation.
- **One automatic retry for content generation.** The core-material and HTML stages each retry once on an incomplete generation before failing clean, improving reliability on the nondeterministic free fallback.
- **DeepSeek read timeout** reduced from 90s to 8s (env `DEEPSEEK_TIMEOUT_SECONDS`) so an unreachable primary fails fast to the fallback chain.
- **Removed the AI “smart title” generation** call from the message route (it added an extra provider round-trip per first message); session titles now use the local prompt-derived fallback only.
- **Tightened the planner budget.** The planner’s `max_tokens` was reduced from 2048 to 512 — a plan is a small `{"tool","args"}` JSON, so the tighter budget is faster, cheaper, and less likely to stall on a slow provider.
